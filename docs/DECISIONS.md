# Decisions

A running log of decisions made for MVT Order Hub. Newer entries at the bottom.

## Product / platform decisions

- React, Vite, and TypeScript are used for the frontend.
- Supabase is the backend platform (Auth, PostgreSQL + RLS, Storage, Edge Functions, Queues/Cron).
- Delegated Microsoft OAuth is the provisional choice for connecting Outlook in the demo.
- The final decision on individual vs. shared mailbox connection is still pending.
- Mock email and attachment data will be used for development/testing until real anonymized samples are provided.
- The application will send validated order data to a configurable external outbound API.
- Direct AscendTMS integration is not part of the current implementation.
- ChatGPT owns the approved UI/CSS specifications for this project.
- Claude Code implements the supplied UI specifications and must not invent or redesign the final interface.
- Sensitive secrets and integrations (Microsoft Graph, service role key, outbound API credentials) remain backend-only, inside Supabase Edge Functions.

## Phase 1 technical decisions

- **Package manager**: npm — matches the existing `package-lock.json`.
- **Router style**: `react-router-dom` v7 declarative `<BrowserRouter>` + `<Routes>/<Route>`, not a data router — simplest fit for placeholder-only pages; can migrate to a data router later if loaders/actions become useful.
- **Imports**: plain relative imports; no `@/` path alias yet, to avoid touching `tsconfig`/`vite.config.ts` beyond what Phase 1 needs.
- **Supabase client**: `src/lib/supabaseClient.ts` validates `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` and throws a clear error if either is missing — no fallback/fake values. The module is not imported or initialized anywhere yet; it is wired up when real auth lands in Phase 2.
- **Query client**: a single shared `QueryClient` instance (`src/lib/queryClient.ts`) with default configuration; no devtools installed yet.
- **Auth guard**: not implemented in Phase 1. A `ProtectedRoute` wrapper around the `AppLayout` route group is planned for the next phase.
- **Styling**: `src/index.css` kept minimal and neutral in Phase 1 — only the Vite demo styling was removed. No final dashboard/sidebar/brand design has been implemented.

## Phase 6 technical decisions

- **Outbound API URL editing**: the non-secret outbound API URL seeded into `app_settings` (Phase 6b) is now admin-editable from Settings ("API extern" section). Reads stay a direct client-side `select` (already permitted by the `app_settings_select_admin` RLS policy); writes go through a new `update-outbound-api-setting` Edge Function using the service-role client, since `app_settings` has no client-writable RLS policy. The outbound API credential remains an Edge Function secret (`OUTBOUND_API_KEY`) and is never exposed in this UI.

## Phase 7a technical decisions

- **Extraction pipeline wiring**: `fetch-outlook-message` now calls a new `process-email-job` Edge Function (same internal-fetch pattern already used for `download-attachments`) right after attachments are downloaded, so every ingested email is deterministically parsed automatically — no separate extraction queue/cron was introduced; `extraction_jobs` itself is the durable per-attempt record. `emails.status` now progresses `new` → `processing` → `extracted`/`needs_validation`; the brief's `queued` state is intentionally represented by `email_ingest_queue.status` rather than duplicated onto `emails.status`, since the `emails` row doesn't exist until the queued item is claimed.
- **Reusing `src/lib/extraction/*` from Deno**: rather than duplicating the parser library, `process-email-job` imports it directly via relative paths. Its npm dependencies (`papaparse`, `exceljs`, `unpdf`, `html-to-text`) are bare specifiers that Deno can't resolve on its own — fixed with `supabase/functions/deno.json` (an `"imports"` map to the pinned `npm:` equivalents), which Deno auto-discovers; the CLI's `--import-map` flag pointing at a legacy `import_map.json` did **not** work in local testing and was removed. Binary parser functions (`parseCsv`/`parseXlsx`/`parsePdf`) are typed against Node's `Buffer`; `process-email-job` wraps downloaded Storage bytes via `Buffer.from(...)` using Deno's built-in `node:buffer` compat, with no changes to the library itself. Verified end-to-end with `supabase functions serve` against a real XLSX + a real digital PDF (correct field extraction, correct per-field source/confidence) and a real scanned/no-text-layer PDF (correctly flagged "needs OCR/validare", order created with the fixed note field, `needs_validation`).
- **AI fallback and legacy `.xls` remain out of scope** for this phase (no AI provider chosen yet per the brief's own open-decisions list; `.xls`, pre-2007 binary Excel, isn't supported by the underlying `exceljs` library) — unchanged from before this work.

## Phase 7a-2 technical decisions

- **Confidence threshold made admin-configurable**: `app_settings` key `confidence_threshold` (`{"threshold": 0.85}`, same shape convention as `outbound_api`), read directly client-side and by services via their own service-role client, written through a new `update-confidence-threshold-setting` Edge Function (mirrors `update-outbound-api-setting` exactly). Replaces the three previously hardcoded, mutually inconsistent values in `orderFields.ts` (0.6), `ConfidenceBadge.tsx` (0.85/0.6), and `process-email-job` (0.85). `ConfidenceBadge` was collapsed from an invented 3-tier green/amber/red scheme to 2-tier (green ≥ threshold, red below) — the brief only ever defines one configurable threshold, and the old amber boundary was never brief-sourced.
- **Import-readiness gate, shared between client and server**: new `src/lib/orders/importReadiness.ts` is imported by both `ActionBar.tsx` and `submit-order` (same cross-boundary Deno-import pattern 7a-1 established for the extraction library) — a single implementation, not duplicated, since client/server drift on this specific rule is exactly what the audit flagged. Required fields per brief 5.5: `client_order_number`, `client_name`, `pickup_address`, `delivery_address`, `pickup_at`, `delivery_at`, `cargo_type`, plus at least one of `quantity`/`weight_kg`/`volume_m3`. `transport_amount`/`currency`/`carrier_proposed` are deliberately not required — the brief conditions them on "if the flow requires it," which nothing yet configures. Only required fields can block import (missing, or present with confidence below the configured threshold); a low-confidence *non-required* field (e.g. `notes`) does not block, though it still counts toward the existing informational "N fields below threshold" pill elsewhere in the UI.
- **`needs_validation` → import in one step**: `submit-order`'s `ELIGIBLE_STATUSES` is unchanged (still includes `needs_validation`) — since no manual-correction UI exists yet to move an order into a distinct `ready_to_import` state, the readiness check itself now serves as the "Gata de import" gate the brief describes, enforced at click/request time rather than via a separate status transition. A distinct "mark as ready" step was considered and rejected: it would add friction without adding safety, since it wouldn't check anything the automatic gate doesn't already check.
- **Deno import-extension fix**: `orderFields.ts`'s imports of `../emails/format` and `../emails/types` (including its `import type`) needed explicit `.ts` extensions to be importable from `submit-order` — confirmed Deno's edge-runtime resolves `import type` specifiers during graph-building too, not just value imports (an assumption from 7a-1 that turned out to be wrong in practice). Verified TS-legal via `tsconfig.app.json`'s `allowImportingTsExtensions: true`.
- Verified end-to-end with `supabase functions serve`: a complete high-confidence order imports; a missing required field 409s naming the field; a present-but-low-confidence required field 409s naming the field; changing the threshold via the new Edge Function shifts the same unchanged order from blocked to importable and back.

## Phase 7a-4 technical decisions

- **`emails` dedup key is now `(graph_message_id, connection_id)`, not `graph_message_id` alone**: two `mail_connections` rows already exist for this project (confirmed while diagnosing the Outlook connection), so a global unique constraint could have silently attributed a message to the wrong connection. `connection_id` is nullable (existing seed/mock rows have none); `fetch-outlook-message` always has a real one at upsert time.
- **Attachment SHA-256 duplicate signal is soft, not a block**: computed in `process-email-job` (query `email_attachments` for the same hash on a *different* email whose order already reached `imported`/`importing`) and surfaced as a warning appended to the order's `notes` field — the same mechanism already used for the scanned-PDF/needs-OCR note. A supplier resending the identical file for a legitimate follow-up order is a real case; only brief 6.4's client_order_number+client_name+status check (in `submit-order`) is a hard block. The brief's separate "sender + client_order_number checksum" wasn't built as its own mechanism — it's functionally the same question `submit-order`'s hard-block query already answers, so a second checksum column would have been redundant complexity with no behavioral difference.
- **`download-attachments` now enforces a hardcoded 25 MB/file limit** (brief's own recommended default) checked against Graph's reported `size` before decoding `contentBytes` — not promoted to `app_settings`, unlike the confidence threshold, since nothing suggests it needs runtime tuning yet. Oversized attachments are skipped (logged, no `email_attachments` row), matching the function's existing per-attachment error isolation.
- **`download-attachments` also enforces a `SAFE_ATTACHMENT_EXTENSIONS` security allow-list** (brief 11.1: "validare MIME/size") — `.csv/.xlsx/.xls/.pdf/.docx/.doc/.jpg/.jpeg/.png/.gif/.bmp/.webp/.txt`, checked via the same `extensionOf()` helper used for the storage key, right after the size check. Anything outside this list (e.g. `.exe`, `.html`) is skipped the same way (logged, no row) rather than being stored and made downloadable — this is deliberately broader than `process-email-job`'s separate, narrower `isCsv`/`isXlsx`/`isPdf` parsing-eligibility check, which stays unchanged and still governs only what gets parsed for order fields, not what gets stored.

## Phase 7a-5 technical decisions

- **Attachment open/download via signed URL, no client-side storage RLS**: new `get-attachment-signed-url` Edge Function — any authenticated *active* profile (no role check, mirrors `submit-order`'s pattern) may request a signed URL for any attachment id, matching the existing `email_attachments_select_active_profile` policy, which already exposes attachment metadata with the same zero-scoping. The bucket stays private with no `storage.objects` policies, exactly as the bucket-creation migration originally intended. Signed URLs expire in 120s (brief 7.3/11.1: "durată scurtă").
- **One uniform "Deschide" action, not separate preview/download buttons**: the same signed URL is just `window.open()`ed in a new tab for every attachment type — the browser's own `Content-Type` handling renders PDFs/images inline (satisfying "preview") and downloads everything else natively, so no client-side branching by file kind was needed to satisfy brief 9.2's "preview și descărcare."
- **`createSignedUrl`'s `download` option is passed the original filename** (`email_attachments.filename`, fetched in the same lookup as `storage_path`), so the browser saves/displays the file under a human-readable name (e.g. `factura.pdf`) via `Content-Disposition`, even though the actual storage key stays the randomized `sha256+extension` from Phase 7a-4 — verified directly: the response header was `content-disposition: attachment; filename=factura-comanda-real.pdf`, not the storage path's hash, and the downloaded bytes' own sha256 matched the storage key exactly (genuine file content, not corrupted).
- Not consolidating `PendingOrderAttachments.tsx`'s and `EmailDetailPanel.tsx`'s duplicated `FileTypeIcon` logic into one shared `AttachmentCard` component (brief 9.2 names one) — out of scope for this phase, both got the same new button independently via a shared `useOpenAttachment` hook instead.
- **Storage keys are content-addressed (`${email_id}/${sha256}${extension}`), never the sender-controlled filename** (brief 11.1: "denumiri randomizate"). The original filename is preserved only in `email_attachments.filename` for display.

## Phase 7a-6 technical decisions

- **`audit_logs` now covers login, Outlook connect, and import** (brief 11.1) — corrections and rejection stay out of scope, since neither exists as a real feature yet (disabled stub buttons). A failed audit insert never fails the parent action, for all 4 actions now covered (matches the pre-existing settings functions' pattern exactly): try/catch around the insert only, `console.error`, execution continues.
- **Login**: a small new `log-login` Edge Function, not a Supabase Auth Hook — this repo has no existing Auth Hook infrastructure, the closest available hook fires on every password-verification attempt (including failures) rather than cleanly on success, and a small function matches every other write in this codebase and can be verified with `supabase functions serve` the same way. Called fire-and-forget from `LoginPage.tsx` right after a successful `signInWithPassword`, never blocking navigation.
- **Outlook connect's actor_id problem**: `outlook-oauth-callback` has `verify_jwt = false` and is invoked directly by Microsoft's redirect — no Supabase session or Authorization header ever reaches it, so there was no way to know who initiated the connection. Fixed by extending the OAuth `state` param (already HMAC-signed for CSRF protection) from `nonce.issuedAtMs.signature` to `nonce.issuedAtMs.userId.signature` in `outlook-oauth-start` (which already knows the calling admin) — `outlook-oauth-callback` now recovers and verifies that `userId` alongside the existing tamper/expiry checks, and uses it as the `connect` audit entry's `actor_id`. The admin's own user id traveling through their own browser's redirect isn't sensitive; it's signed, so it can't be forged.
- Verified end-to-end with `supabase functions serve`: a real login produces an `audit_logs` row with the correct `actor_id`; a real `submit-order` import produces a row with `old_data.status: 'needs_validation'` → `new_data.status: 'imported'`. The full `outlook-oauth-start` → `outlook-oauth-callback` state round-trip can't complete locally (the callback needs a genuine Microsoft token exchange after the state check, same limitation as every other Outlook-related phase) — instead verified in three parts: the real `outlook-oauth-start` mints a real signed 4-part state containing the real admin's user id; the real `outlook-oauth-callback` does not reject that state as invalid (fails later, at the expected token-exchange step, not at the state check); and an exact logic replica of `checkState()` run against that same real state independently recovers the identical user id.
- Verified end-to-end (`supabase functions serve` for `process-email-job`/`submit-order`; `download-attachments`' new per-attachment logic verified against real local Storage/DB directly, since its Graph-dependent fetch step can't be exercised without a live Microsoft Graph connection, same limitation noted diagnosing the Outlook webhook path): a duplicate `client_order_number`+`client_name` import attempt 409s; a reused attachment hash produces the warning note without blocking; a 26 MB attachment is skipped with no DB row; a `.exe`/`.html` attachment is skipped with no DB row; a `.docx`/`.png` attachment (both allow-listed) is stored with a randomized path and visible, but contributes no order fields.

## Phase 7a-7 technical decisions

- **Manual correction writes both `orders` and `order_field_sources`, not either/or**: `ORDER_FIELD_SECTIONS`' `value()` reads directly from `orders` columns (what's displayed and what `submit-order` sends onward), while confidence/readiness/badges all read `order_field_sources` via `latestSourceFor()` — a correction has to update both to stay consistent. `correct-order-fields` does each as a single batched statement (one `UPDATE orders` covering every changed column, one multi-row `INSERT` into `order_field_sources` covering every changed field) rather than looping per field, matching `process-email-job`'s existing `fieldSources` insert pattern.
- **No DB transaction/RPC wraps the two writes** — if the `order_field_sources` insert fails after the `orders` update already succeeded, the function returns a real error (not 200), so the caller is never told a correction saved when only half of it did. Verified directly: temporarily revoked the local service role's `INSERT` grant on `order_field_sources`, ran a correction, confirmed `orders.client_name` was updated but the function returned `500` with an explicit "correction is INCOMPLETE" message and zero `order_field_sources` rows existed — then restored the grant and confirmed a normal correction succeeds again.
- **Import-readiness needed zero code changes** — `latestSourceFor()` already resolves "the" source for a field as whichever `order_field_sources` row has the latest `created_at`, so a fresh manual row (`confidence: 1`) automatically supersedes the old extracted one. Verified concretely: an order with a below-threshold `client_name` confidence (0.3) was refused import by `submit-order`'s readiness check before correction, and imported successfully immediately after correcting just that one field — no other code touched.
- **Correction scope, v1**: only the 13 fields `ORDER_FIELD_SECTIONS` already represents as their own row are editable — `quantity_unit`/`currency` (which only ride along inside `quantity`'s/`transport_amount`'s display string) are not independently correctable this pass. Corrections and rejection are both refused (`409`) once an order/email is past the pre-import stage (`importing`/`imported`/`rejected`) — matches brief 6.3's per-status action table.
- **Single edit-mode toggle, not per-field inline editing**: `useOrderCorrection` (a shared hook, not duplicated per page) owns draft values and the save mutation; `ActionBar`'s amber button toggles `Corectează manual` ⟷ `Salvează corectările`. `EmailDetailPanel`/`EmailsPage` renders a different, smaller read-only component (`OrderFieldsSummary`, not `PendingOrderFields`) and gets rejection but not correction — `ActionBar`'s correction props are optional, and the button stays disabled there with an accurate title rather than pretending the feature doesn't exist.
- **Rejection cascades to an email's orders, but only pre-import ones**: rejecting an email without also rejecting its still-open order(s) would leave them sitting in a status `submit-order`'s `ELIGIBLE_STATUSES` still accepts — a real correctness gap, not cosmetic. Already-`importing`/`imported` orders are deliberately left untouched (retroactively flipping a completed import would be destructive). One `audit_logs` row for the email plus one per cascaded order. Confirmation via a plain `window.confirm(...)`, no reason collected this pass (brief allows it to be optional).

## 2026-07-30 — "Extrage Automat cu AI" (manual AI re-extraction)

- **First real AI provider wired into the codebase**: everything extraction-related up to this point (`process-email-job`, `src/lib/extraction/*`) is deterministic JS/TS parsing only — no LLM call existed anywhere, confirmed by grepping the whole repo for an API key/provider reference before starting this work. `src/lib/extraction/aiFallback.ts`'s `AiFallbackProvider` interface (for automatic hybrid-mode fallback *during* initial extraction) was, and still is, unimplemented. No AI provider had been chosen anywhere in the docs (Phase 7a's decision log entry says so explicitly), so **OpenAI** (`gpt-4o-mini`, Chat Completions, JSON mode) was picked as the first concrete provider — the most standard default for a Deno Edge Function doing structured JSON extraction, not an arbitrary choice made without checking for an existing convention first. The key is read from `OPENAI_API_KEY`, an Edge Function secret (`supabase secrets set OPENAI_API_KEY=...`) — never checked into `.env.example`/`.env.local`, same rule already established there for every other server-side credential.
- **New `extract-order-ai` Edge Function, not a rebuild of the existing `retry-extraction`**: `retry-extraction` (already implemented, pre-existing) re-runs the same deterministic `process-email-job` pipeline and only accepts an email whose latest `extraction_jobs` row is `failed` — a different, narrower use case than a manually-triggered "try AI now" pass on an already-extracted order. `extract-order-ai` takes `order_id`, is available whenever the order's status is pre-import (`draft`/`needs_validation`/`ready_to_import`/`import_failed`, same set `correct-order-fields`/`ActionBar` already use), and only fills fields that are still `null` or below the configured confidence threshold — it never overwrites a field the deterministic parser was already confident about. Context sent to the model is the email body (already-sanitized `emails.body_text`, or `sanitizeEmailBodyToText` on `body_html`, reused from `src/lib/extraction`) plus best-effort raw text of PDF/CSV attachments (XLSX raw-text extraction was left out of this pass — the deterministic parser already handles XLSX well, and this button exists specifically to cover what it *couldn't* read from the email/PDF/CSV text).
- **`extraction_jobs.mode = 'ai'` and `order_field_sources.source_type = 'ai'`**: both values already existed in the Phase 3 schema's CHECK constraints (unused until now) — this function is the first thing to actually write them, not a new column/constraint.
- **Response validation, not blind trust of the model's output**: the function only accepts a field back if it was one of the ones actually requested (the model is instructed not to guess, but isn't trusted not to); numeric/date/currency fields are coerced and rejected if invalid instead of stored as-is. `confidence_overall` is recomputed with the exact same "mean across all 15 leaf fields" formula `mapToOrderRow.ts` already uses, so a partial AI fill produces a comparable number to a fresh deterministic parse, not a differently-scaled one.
- **Button wiring matches `ActionBar.tsx` exactly**: `PendingOrderTopBar.tsx`'s new mutation is a `useMutation` calling `supabase.functions.invoke('extract-order-ai', ...)`, invalidates the shared `['emails', 'list']` query on settle, and uses the same text-only pending state (no spinner icon — `ActionBar` doesn't use one either) and the same inline `role="alert"` error-paragraph pattern as `submitMutation`/`rejectMutation`/etc. No new UI pattern was invented for this button.
